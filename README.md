# Telegram-бот «Заявки сисадмину» (MVP)

Бот приёма заявок системному администратору внутри компании.
aiogram 3 + SQLite, интерфейс на русском, Docker.

## Статус по этапам

| Этап | Содержание | Статус |
|---|---|---|
| 1 | Фундамент: конфиг, FSM-состояния, 5 таблиц + CRUD, middlewares, клавиатуры, callback-схема | ✅ готов |
| 2 | Пользователь: создание заявки, публикация на доску | ✅ готов |
| 3 | «Мои заявки»: листы, карточка, отмена | ✅ готов |
| 4 | Админ: меню, листы, карточка, в работу/ответ/закрыть | ✅ готов |
| 5 | Доска: кнопки `b:*`, редактирование с fallback | ✅ готов |
| 6 | TTL FSM, тесты, Docker-сборка | ✅ готов |

Работает: `/start` (роль → меню), `/help`, `/cancel`, полный сценарий
создания заявки — описание с фото/видео (альбом собирается), приоритет, место
(или из профиля), предпросмотр, создание `#0001`, вложения в БД, публикация на доску,
запись в `logs` + `LOG_CHAT_ID`. «Мои заявки» — листы, карточка, отмена из `waiting`.
Админка — листы «Ожидают/В работе/Все», карточка, «В работу», «Ответить», «Закрыть»,
пересылка вложений. Доска — кнопки «В работу/Закрыть», редактирование с fallback.
FSM-состояния истекают через `STATE_TTL`.

## Запуск

```bash
cp .env.example .env      # Windows: Copy-Item .env.example .env
# заполнить BOT_TOKEN, TICKETS_CHAT_ID, ADMIN_IDS
docker compose up -d --build
docker compose logs -f bot
```

Локально: `pip install -r requirements.txt && python -m bot.main`.

## Docker

Образ проверен: `python:3.14-slim`, внутри Python 3.14.10, aiogram 3.31.0,
SQLAlchemy 2.0.57, pydantic 2.13.5; размер 261 МБ; процесс идёт от `botuser` (uid 1000).
При старте создаётся `/app/data/bot.sqlite3` (том `bot_data`) со всеми 5 таблицами
и индексами. Неверный токен даёт понятную строку в логе и код возврата 1,
без трейсбека и «unclosed session»:

```
INFO  | __main__ | Бот остановлен
ERROR | __main__ | Telegram отклонил BOT_TOKEN — проверьте значение в .env
```

Проверки, выполненные на сборке: `docker compose config`, `docker build`,
запуск контейнера с фиктивным токеном (выход на api.telegram.org и 401),
проверка uid, импорт `bot.main`, схема SQLite в томе.

## Один чат с топиками

Заявки и логи могут жить в одной форум-супергруппе, в разных темах.

1. Включите в группе «Темы» (Topics), создайте темы **«Заявки»** и **«Log»**.
2. Добавьте бота в группу; надёжнее всего — администратором с правом отправки сообщений.
3. Возьмите ID темы: откройте любое сообщение в теме → «Копировать ссылку»:
   `https://t.me/c/1234567890/10/20` → тема `10` (или `20` — id первого сообщения темы).
4. Заполните `.env`:

```ini
TICKETS_CHAT_ID=-1001234567890
TICKETS_THREAD_ID=10
LOG_THREAD_ID=20
# LOG_CHAT_ID не задаём: логи пойдут в тот же чат, в тему 20
```

Без `TICKETS_THREAD_ID` бот пишет в General/обычный чат — обратная совместимость
сохраняется. Редактирование карточки работает по `message_id` и тему не требует;
если сообщение удалили и бот отправляет новое, оно уходит в ту же тему.
Уведомление об отмене заявки тоже публикуется в теме «Заявки», а не в общем потоке.

## БД

`users(tg_id, place, is_admin, created_at)` ·
`tickets(number, user_id, author_name, author_username, description, priority, place, status, tg_message_id, created_at, updated_at)` ·
`attachments(ticket_id, file_id, file_type, kind)` ·
`admin_replies(ticket_id, admin_tg_id, text, created_at)` ·
`logs(ts, actor_tg_id, action, ticket_id, payload_json)`

Статусы: `waiting → in_progress → closed | cancelled`. Приоритеты: `low | medium | high`.
Имя автора — снапшот в заявке, ссылка `tg://user?id=...` строится из `users.tg_id`.

## Callback-и

| Префикс | Пример | Назначение |
|---|---|---|
| `u:` | `u:new`, `u:list:1`, `u:menu`, `u:help`, `u:cancel`, `u:place:default` | пользовательское меню |
| `prio:` | `prio:medium` | приоритет |
| `t:` | `t:5:card`, `t:5:cancel` | карточка/действия по заявке |
| `act:` | `act:5:take`, `act:5:reply`, `act:5:close`, `act:5:files` | действия админа в боте |
| `a:` | `a:list:waiting:1`, `a:menu`, `a:cancel` | админ-листы |
| `b:` | `b:5:take`, `b:5:close` | кнопки на доске |

## Сценарий создания заявки

`u:new` → описание (текст и/или фото, видео одним сообщением; альбом склеивается за 1.2 с,
подпись берётся из первого файла) → приоритет → место (кнопка «🏢 …» подставляет
последнее место из `users.place`) → предпросмотр → `u:send`.

Место из **каждой** созданной заявки сохраняется в `users.place`, поэтому кнопка
«🏢 место из профиля» всегда предлагает последнее использованное.

Заявку можно отправить и **без кнопки**: любое сообщение в личке вне активного
диалога (текст и/или фото, видео) считается описанием — бот сразу предлагает
приоритет. Так ничего не теряется, если человек пишет боту как в обычный чат.
Сообщения из групп, команды и сообщения админов заявок не создают.

При отправке: заявка получает номер, вложения пишутся с `kind='ticket'`, публикуется
карточка на доске с кнопками, пишется лог `ticket_created`. Если доска недоступна,
заявка всё равно создаётся, пользователь видит предупреждение, в лог уходит `board=False`.
Повторный клик по «Отправить» дубль не создаёт: состояние снимается до записи в БД.

## Мои заявки и отмена

`u:list:<page>` показывает только `waiting`/`in_progress`, по `PAGE_SIZE` на страницу,
строки — inline-кнопки `t:<id>:card`, навигация `u:list:<page±1>`, `u:menu`.
Карточка: номер, приоритет, статус, место, дата, описание, число файлов,
`t:<id>:cancel` (только `waiting`) и `t:<id>:back` (номер страницы хранится в FSM-данных).

Отмена: проверка владельца через `get_user_ticket` (join по `users.tg_id`) и статуса
`waiting`; затем `status=cancelled`, редактирование карточки на доске с текстом
«❌ Отменена пользователем» и снятием кнопок (пустая `InlineKeyboardMarkup` — иначе
Telegram оставил бы старые), уведомление в `TICKETS_CHAT_ID`, запись в `logs`
(`ticket_cancelled`). Если сообщение доски изменить нельзя — отправляется новое,
`tg_message_id` обновляется.

## Админ-флоу

`/start` для ID из `ADMIN_IDS` открывает админ-меню: «🆕 Ожидают», «🔧 В работе», «📜 Все»
(`a:list:<tab>:<page>`, пагинация, строки — `t:<id>:card`). «Все» включает `closed`/`cancelled`.

Карточка: номер, приоритет, статус, место, кликабельный автор `tg://user?id=`,
описание, число вложений, последние ответы. Действия: `act:<id>:take` (только `waiting`),
`act:<id>:reply`, `act:<id>:close`, `act:<id>:files` / `act:<id>:hide_files`:
«Показать вложение» удаляет сообщение-меню и отправляет новое — с медиа и подписью-карточкой,
«Скрыть вложение» удаляет медиа и возвращает текстовую карточку. В чате всегда
одно сообщение на заявку, файлы не копятся. Листание — `file:<id>:<n>`.

Ответ: «Ответить» редактирует карточку в сообщение ожидания (с «Отмена»); после
отправки ответа карточка возвращается тем же сообщением, а сообщение админа
удаляется из чата — в переписке остаётся только меню, без мусора. Ответ может быть
текстом или фото/видео, альбом собирается `AlbumMiddleware`. Доставка пользователю
через `copy_message` / `copy_messages` (медиа и форматирование сохраняются),
текст пишется в `admin_replies`, файлы — в `attachments` с `kind='admin_reply'`,
карточка на доске обновляется, в `logs` — `admin_reply`. Ответ на
закрытую/отменённую заявку отклоняется.

Карточка `t:<id>:card` одна на обе роли: админу рендерится админ-вид с действиями,
пользователю — его вид с отменой.

## Доска

Одно сообщение = одна заявка, `tickets.tg_message_id` хранится. Кнопки: `b:<id>:take`
(только из `waiting`) и `b:<id>:close`; после смены статуса клавиатура пересобирается,
для финальных статусов кнопки снимаются пустой `InlineKeyboardMarkup`.

Любое изменение (взятие, закрытие, ответ админа, отмена) редактирует то же сообщение.
Если `edit_message_text` невозможен (`message to edit not found`, `can't be edited`) —
отправляется новое сообщение, `tg_message_id` обновляется. `message is not modified`
считается успехом, дубль не отправляется.

Кто и когда менял статус, показывается строкой «🛠 Изменил: <имя админа> · дата»:
имя сохраняется в `payload` лога (`ticket_taken` / `ticket_closed`) в момент действия,
поэтому схема `tickets` не расширяется. Для старых записей без имени — «администратор».

Telegram подменён мок-сессией, БД — временный SQLite, реальная сеть не нужна.

## Безопасность: SQL-инъекции

- Все запросы идут через SQLAlchemy ORM/Core (`select`, `update`, `.in_()`), без
  `text()`, `executescript` и f-строк в SQL; значения передаются bind-параметрами
  (`?`), идентификаторы (таблицы, колонки, `ORDER BY`) статические.
- Пользовательские строки — описание, место, имя автора, текст ответа, `file_id`,
  JSON логов — попадают только в значения.
- Callback-данные валидируются до запроса: id через `isdigit()` → `int`, вкладка
  админки по белому списку `waiting|in_progress|all`, страница через `isdigit()`.
- Приоритет и статус преобразуются через `Priority(...)`/`TicketStatus(...)`,
  неизвестное значение отклоняется.
- `DB_PATH` — доверенная настройка окружения (из неё строится DSN), а не
  пользовательский ввод; менять её может только владелец сервера.
- Тесты: `tests/test_sql_injection.py` — 7 payload'ов (`DROP`, `DELETE`, `UPDATE`,
  `OR 1=1`, `ATTACH`), проверка сохранения «как есть», целостности схемы и того,
  что запрос компилируется с `?`, без текста payload'а.
- `bandit -r bot`: 0 medium/high, предупреждение B608 (SQL injection) отсутствует.

HTML в сообщениях экранируется `html.escape` при `parse_mode=HTML` — отдельная
поверхность (HTML-инъекция) закрыта.

## TTL состояний

`MemoryStorage` TTL не умеет, поэтому стоит `StateTTLMiddleware`: если пользователь
не присылал апдейтов дольше `STATE_TTL` (по умолчанию 900 с), состояние очищается
перед обработкой нового апдейта. Клики по устаревшим кнопкам (`prio:*`, `u:send`,
`u:place:default`) отвечают «Сессия истекла, начните заново».

## Если контейнер падает с ValidationError

```
pydantic_core._pydantic_core.ValidationError: 2 validation errors for Settings
bot_token        Field required [input_value={}]
tickets_chat_id  Field required [input_value={}]
```

Это значит, что контейнер запущен **без окружения**: `.env` не копируется в образ
(там секреты) и должен передаваться при запуске.

- **Compose:** `.env` лежит рядом с `docker-compose.yml`; применить изменения —
  `docker compose up -d --force-recreate`. Команда `docker compose start` не
  перечитывает `.env`, а `up` без `--force-recreate` может оставить старый контейнер.
- **`docker run`:** обязателен `--env-file .env`, иначе переменных нет:
  `docker run -d --name tgbot --env-file .env --restart unless-stopped -v tgbot_bot_data:/app/data tgbot:local`.
- **Проверка:** `docker compose run --rm --no-deps bot python -c "from bot.config import get_settings; s = get_settings(); print(bool(s.bot_token), s.tickets_thread_id, s.log_thread_id)"`.

С версии с этой проверкой бот сам пишет, каких переменных не хватает, и выходит с кодом 2.

## Известное

- FSM хранится в памяти: после рестарта активные диалоги теряются (для MVP допустимо;
  при необходимости заменяется на RedisStorage).
- Авторство смены статуса читается из `logs`; при росте объёма стоит денормализовать
  в `tickets.admin_tg_id`/`taken_at`.
